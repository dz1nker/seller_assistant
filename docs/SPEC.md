# Техническое задание для Codex
# Sales Copilot — AI CRM для продаж через мессенджеры

## 0. Твоя роль и основные требования

Ты — senior full-stack разработчик, системный архитектор и UI/UX-инженер.

Необходимо разработать рабочее SaaS-приложение Sales Copilot для экспертов, консультантов, блогеров и других специалистов, которые продают свои продукты и услуги через личные сообщения.

**Главная задача продукта:** помогать пользователю управлять коммерческими переписками, анализировать ситуацию по каждой сделке и предлагать наиболее подходящие следующие сообщения для продвижения клиента к покупке.

Приложение должно совмещать:

1. Полноценный интерфейс мессенджера.
2. Подключение личного Telegram-аккаунта через MTProto/TDLib.
3. Отправку и получение сообщений непосредственно из приложения.
4. CRM с клиентами, сделками и канбан-доской.
5. ИИ-помощника по продажам.
6. Базу знаний о бизнесе и продуктах пользователя.
7. Управление задачами и напоминаниями.
8. Основу для будущей интеграции Instagram.

### Ключевой принцип

**ИИ предлагает — пользователь решает и отправляет.**

ИИ не должен самостоятельно отправлять сообщения клиентам.

Пользователь должен иметь возможность выбрать рекомендацию ИИ, отредактировать её прямо в поле ввода и отправить через подключённый мессенджер.

Не создавай имитацию работающего продукта, состоящую из статических экранов. Необходим функциональный backend, реальная база данных, рабочие API и работающая интеграция Telegram.

Если для функции требуются внешние ключи или разрешения, реализуй полный технический механизм, конфигурацию, обработку ошибок и тесты, а подключение выполняй через переменные окружения.

Не выдумывай успешное подключение внешних сервисов.

# 4. Telegram Gateway

## 4.1. Принцип работы

Использовать официальный Telegram MTProto API через TDLib.

Не использовать Telegram Bot API как основной способ подключения личного аккаунта.

Приложение должно использовать собственные Telegram API credentials, передаваемые через переменные окружения:

```env
TELEGRAM_API_ID=
TELEGRAM_API_HASH=
```

Не хранить API hash в frontend или публичном JavaScript.

## 4.2. Подключение Telegram

В настройках реализовать кнопку «Подключить Telegram».

Авторизация должна поддерживать необходимые состояния TDLib:

- Ввод номера телефона.
- Подтверждение кодом.
- Дополнительную проверку email, если потребуется.
- Двухфакторную защиту.
- Подтверждение с другого устройства, если потребуется.
- Успешное подключение.
- Ошибку авторизации.
- Отключение аккаунта.

Интерфейс должен отображать текущее состояние подключения.

После успешного подключения сохранять только необходимые идентификаторы и защищённые данные сессии.

Сессии TDLib разных пользователей необходимо изолировать.

## 4.3. Список диалогов

Получать доступный список чатов подключённого аккаунта.

В интерфейсе отображать:

- Имя собеседника.
- Username, если доступен.
- Аватар, если доступен и разрешён.
- Тип чата.
- Последнее сообщение для разрешённых диалогов.
- Время последней активности.
- Количество непрочитанных сообщений.
- Признак выбранного клиента.
- Статус активной сделки.

При этом предусмотреть ограничения на хранение и использование данных личных диалогов.

Запрещено направлять личные или исключённые переписки на ИИ-анализ.

## 4.4. Открытие переписки

При открытии разрешённого диалога отображать историю сообщений с пагинацией.

Поддержать первоначально:

- Текстовые сообщения.
- Эмодзи.
- Ссылки.
- Ответы на сообщения.
- Дату и время.
- Статусы отправки.
- Отображение вложений с учётом разрешений.

Для неподдерживаемых типов сообщений показывать корректные заглушки, а не ошибку приложения.

## 4.5. Отправка сообщений

Это обязательная функция MVP.

Внизу каждого диалога должно находиться полноценное поле ввода.

Пользователь может:

1. Написать сообщение самостоятельно.
2. Использовать предложенное ИИ сообщение.
3. Отредактировать предложенное сообщение.
4. Отправить его из текущего интерфейса.

Для Telegram использовать `sendMessage` через TDLib.

Реализовать состояния:

```text
draft
pending
sending
sent
failed
```

Не путать принятие команды отправки с фактическим подтверждением Telegram.

При ошибке показать сообщение пользователю и предложить повторить отправку.

Не допускать дублирующей отправки при повторных нажатиях или сетевых сбоях.

Предусмотреть idempotency key на уровне команд приложения и согласование локального сообщения с подтверждением TDLib.

После перезагрузки страницы не должно происходить повторной отправки.

## 4.6. Синхронизация

Обрабатывать доступные события:

- Новое входящее сообщение.
- Новое исходящее сообщение.
- Редактирование сообщения.
- Удаление сообщения.
- Изменение статуса отправки.
- Изменение состояния подключения.

Сообщения, отправленные пользователем из официального Telegram-клиента, должны появляться в Sales Copilot, если диалог разрешён и событие доступно через интеграцию.

Дедупликацию выполнять по идентификаторам источника, чата и сообщения.

Предусмотреть восстановление после перезапуска сервера.

Не реализовывать обход ограничений Telegram и автоматическую массовую отправку сообщений.

# 5. Приватность диалогов

Это обязательная часть архитектуры.

Каждая переписка должна иметь режим:

```text
EXCLUDED
CANDIDATE
CLIENT
```

### EXCLUDED

Личный или исключённый диалог.

- Не анализировать через ИИ.
- Не сохранять содержимое в CRM.
- Не создавать сделки.
- Не строить профиль собеседника.
- Не индексировать сообщения.

### CANDIDATE

Потенциальный клиент, ещё не добавленный в работу.

- Разрешён минимальный объём технических метаданных.
- Полный ИИ-анализ выключен.
- Пользователь может вручную перевести диалог в CLIENT.

### CLIENT

Диалог, который пользователь выбрал для работы.

- Разрешена предусмотренная политикой синхронизация.
- Доступно создание сделки.
- Доступны CRM-функции.
- Доступны задачи и напоминания.
- ИИ-анализ включается только после отдельной проверки допустимости использования данных.

Создать централизованный Privacy Engine.

Нельзя допустить, чтобы AI Service получал сообщения в обход Privacy Engine.

**Важное юридическое ограничение:** пользовательская отметка CLIENT не считается согласием собеседника на ИИ-обработку. В соответствии с актуальными условиями Telegram такая обработка должна быть отдельно проверена.

Реализовать AI Policy Guard, который по умолчанию запрещает отправку реальной Telegram-переписки во внешнюю LLM. Разрешение может быть предоставлено только в соответствии с подтверждённой политикой конкретного источника и документированными правами/согласиями. Не делать универсальную настройку, позволяющую обойти это ограничение одним переключателем.

Для разработки AI Engine использовать синтетические демонстрационные данные или другие законно и договорно допустимые источники.

Также реализовать:

- Удаление данных клиента.
- Очистку локально сохранённой истории.
- Отключение интеграции.
- Отзыв разрешений.
- Журнал действий с данными.
- Настраиваемые сроки хранения.

# 7. AI Copilot

## 7.1. Задачи ИИ

ИИ должен помогать продавать, но не пытаться продавать любой ценой.

Он должен:

1. Понимать контекст продукта пользователя.
2. Анализировать допустимую историю конкретной сделки.
3. Выделять факты о клиенте.
4. Определять потребности.
5. Находить возражения.
6. Выявлять недостающую информацию.
7. Рекомендовать следующий шаг.
8. Предлагать варианты сообщения.
9. Объяснять свои рекомендации.
10. Предлагать изменение этапа сделки.
11. Подсказывать, когда лучше не продавать.

Не использовать манипулятивные, обманные или агрессивные стратегии.

## 7.2. Архитектура

Создать логические компоненты:

```text
ConversationAnalyzer
DealIntelligence
SalesStrategist
ResponseGenerator
KnowledgeRetriever
AIContextBuilder
AIPolicyGuard
```

### ConversationAnalyzer

Получает допустимый контекст и возвращает структурированные сведения.

### DealIntelligence

Обновляет память сделки и определяет рекомендуемую стадию.

### SalesStrategist

Выбирает следующую стратегию общения.

Примеры стратегий:

```text
clarify_need
answer_question
present_product
handle_objection
provide_case
discuss_payment
follow_up
pause_sales
recommend_alternative
```

### ResponseGenerator

Формирует несколько вариантов следующего ответа.

## 7.3. Варианты сообщений

Для каждой рекомендации предусмотреть три тона:

- Мягкий.
- Уверенный.
- Короткий.

Пользователь должен иметь возможность:

- Выбрать вариант.
- Перегенерировать.
- Попросить сделать короче.
- Попросить сделать подробнее.
- Изменить тон.
- Вставить текст в поле сообщения.
- Отредактировать текст.
- Отправить самостоятельно.

ИИ не должен иметь прямого доступа к методу отправки.

## 7.4. Структурированный результат

Пример JSON:

```json
{
  "summary": "Клиент интересуется программой",
  "facts": [],
  "needs": [],
  "objections": [],
  "missing_information": [],
  "intent": "product_interest",
  "stage_suggestion": "DISCOVERY",
  "recommended_action": "clarify_need",
  "reasoning_summary": "Необходимо уточнить задачу",
  "responses": [
    {
      "tone": "warm",
      "text": "..."
    },
    {
      "tone": "confident",
      "text": "..."
    },
    {
      "tone": "short",
      "text": "..."
    }
  ]
}
```

Результаты проверять через Zod.

Не сохранять произвольный непроверенный JSON.

При ошибке LLM не разрушать состояние диалога.

## 7.5. Факты и гипотезы

Разделять:

```text
CONFIRMED
INFERRED
UNKNOWN
```

Подтверждённые факты должны содержать ссылки на исходные сообщения или другие допустимые источники.

Нельзя представлять предположения как установленные факты.

## 7.6. Память сделки

Не отправлять полную переписку в модель после каждого сообщения.

Использовать:

- Краткое резюме.
- Структурированные факты.
- Последние релевантные сообщения.
- Контекст продукта.
- Историю важных договорённостей.

Хранить версию контекста.

Если после генерации пришло новое сообщение, помечать предыдущую рекомендацию устаревшей.

## 7.7. Защита от prompt injection

Сообщения клиентов и материалы из внешних источников считать недоверенными данными.

Инструкции внутри переписок не должны:

- Изменять системные правила.
- Открывать доступ к другим Workspace.
- Вызывать отправку сообщений.
- Запрашивать секретные ключи.
- Обходить ограничения приватности.

- Позиционирование.
- Подход к работе.
- Основные преимущества.

### Продукты

- Стоимость.
- Формат.
- Продолжительность.

# 9. CRM и канбан

## 9.1. Основные сущности

Не смешивать контакт, диалог и сделку.

```text
Contact
Conversation
Deal
```

Один контакт может иметь несколько диалогов.

Один контакт может иметь несколько сделок.

Одна сделка может быть связана с несколькими разрешёнными диалогами.

## 9.2. Воронка по умолчанию

Создать стадии:

1. Новый лид.
2. Выявление потребности.
3. Презентация.
4. Возражения.
5. Решение / оплата.
6. Успешно.
7. Проиграно.

Пользователь должен иметь возможность:

- Добавлять этапы.

# 16. Интеграция Instagram

В текущем MVP не требуется полноценное подключение Instagram.

Однако архитектура должна позволять добавить отдельный Instagram Adapter без изменений основных моделей CRM.

Создать интерфейс:

```typescript
interface MessagingChannelAdapter {
  getCapabilities(): ChannelCapabilities;

  connect(input: unknown): Promise<unknown>;

  disconnect(connectionId: string): Promise<void>;

  getConversations(
    connectionId: string
  ): Promise<unknown>;

  getMessages(
    conversationId: string,
    cursor?: string
  ): Promise<unknown>;

  sendMessage(
    input: SendMessageInput
  ): Promise<SendMessageResult>;
}
```

Можно изменить сигнатуры для строгой типизации.

Ключевое требование — единая внутренняя модель сообщений.

Не предполагать, что Instagram имеет те же возможности, что Telegram.

При дальнейшей реализации использовать официальный API Meta для профессиональных аккаунтов, с учётом разрешений, правил отправки сообщений и процедуры проверки приложения.

# 20. Критерии готовности MVP

MVP считается готовым, когда выполнены следующие условия:

- Пользователь может зарегистрироваться и войти.
- Может создать и настроить Workspace.
- Может добавить продукты и информацию о бизнесе.
- Может подключить обычный Telegram-аккаунт.
- Может выбрать диалоги для работы.
- Может просматривать разрешённые переписки.
- Может получать сообщения в реальном времени.
- Может писать и отправлять сообщения из Sales Copilot.
- Может создавать сделки.
- Может перемещать карточки по канбан-доске.
- Может видеть задачи и напоминания.
- Может получать ИИ-рекомендации на допустимых данных.
- Может вставить ИИ-рекомендацию в поле ввода.
- Может отредактировать и отправить сообщение сам.
- ИИ не отправляет сообщения автоматически.
- Личные исключённые переписки не анализируются.
- Данные разных Workspace изолированы.
- Приложение восстанавливается после перезапуска.
- Есть тесты критических сценариев.
- Есть документация по установке.
