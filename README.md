# Sales Copilot

Локальная CRM для продаж через личный Telegram: контакты, продукты, сделки, переписка, задачи и помощник для подготовки ответов. Интерфейс на русском, светлая и тёмная темы, мобильная навигация.

Реализованы CRUD контактов и продуктов, профиль бизнеса и текстовая база знаний, несколько воронок с редактируемыми этапами, канбан с историей и контролем одновременных изменений, задачи/напоминания и аналитика. Отдельный Gateway использует настоящую TDLib для авторизации обычного Telegram-аккаунта и ручной отправки сообщений. AI работает на синтетических диалогах и отдельно разрешённых Telegram-диалогах через OpenAI-compatible API. Реальный Telegram по умолчанию закрыт для ИИ; разрешение требует зарегистрированной проверки политики источника и документированных прав на конкретный диалог.

Живой вход в Telegram и внешний LLM требуют ваших ключей и отдельной проверки с аккаунтом. Ключей в репозитории нет. Демопереписки явно отмечены и не выдают себя за Telegram; демосделки исключены из реальных продаж в аналитике. Эта версия предназначена для локального MVP; ограничения публичного SaaS описаны в [SECURITY.md](SECURITY.md).

## Быстрый запуск Windows

Скачайте [ZIP проекта](https://github.com/dz1nker/seller_assistant/archive/refs/heads/main.zip), распакуйте **все** файлы и запустите `START_WINDOWS.cmd`. Нужен Docker Desktop в режиме Linux containers. Node.js на компьютере отдельно не нужен. Launcher сохраняет существующие пароли `.env` и добавляет недостающие внутренние ключи. Подробная инструкция и обновление — [START_HERE_RU.md](START_HERE_RU.md).

Откройте http://localhost:3000/register и создайте свой аккаунт. Общего логина/пароля нет. В разделе «Диалоги» кнопка «Создать демо-данные» позволяет проверить CRM и помощника без внешних аккаунтов.

## Docker на Linux/macOS

Нужны Docker Compose v2 и Node.js 24 для генерации локальной конфигурации:

```bash
node scripts/init-env.mjs
docker compose --profile app up -d --build --wait
```

Без Node.js на хосте конфигурацию можно создать контейнером:

```bash
docker run --rm --user "$(id -u):$(id -g)" -v "$PWD:/project" -w /project node:24-bookworm-slim node scripts/init-env.mjs
```

Открывайте именно `localhost:3000`: он должен совпадать с `WEB_ORIGIN`. Compose запускает PostgreSQL 17, Redis 7, NestJS API, Next.js web и TDLib Gateway. Порты БД/Redis привязаны к loopback; API и Gateway доступны только во внутренней сети Compose. Тома `pgdata`, `redisdata`, `telegramdata` сохраняют данные и сессии между перезапусками. Не удаляйте тома при обновлении.

```bash
docker compose --profile app stop
docker compose --profile app up -d --wait
```

## Подключение личного Telegram

1. Получите собственные `api_id` и `api_hash` на https://my.telegram.org/apps.
2. Запишите их в локальный `.env`: `TELEGRAM_API_ID` и `TELEGRAM_API_HASH`. Никому не отправляйте этот файл.
3. Выполните `docker compose --profile app up -d --wait`, чтобы применить настройки.
4. Откройте «Настройки → Личные аккаунты Telegram → Подключить Telegram». Введите телефон, код Telegram и при необходимости пароль 2FA/email **в интерфейсе приложения**. Авторизация выполняется в фоне: состояние «Ожидаем ответ Telegram…» не означает успешный вход. Следующий шаг появится автоматически после ответа TDLib; повторный запрос того же шага во время ожидания блокируется. Неподдерживаемые шаги не имитируют успех.
5. После состояния «Подключён» нажмите «Получить список диалогов». В «Диалогах» откройте нужный чат и нажмите «Выбрать для работы». Только после этого CRM загрузит сообщения.

TDLib поставляется через закреплённые npm-пакеты `tdl`/`prebuilt-tdlib`; устанавливать её вручную не нужно. Секретные, защищённые и самоуничтожающиеся сообщения не импортируются. В MVP поддержан текст и ответы на сообщения; вложения показаны как неподдерживаемые. Список ограничен первыми 200 чатами, история загружается страницами до 50 сообщений.

Если официальный Telegram работает через встроенный прокси, добавьте в `.env` строку `TELEGRAM_PROXY_URL='ссылка на ваш прокси'`. Поддерживаются ссылки `https://t.me/proxy?...`, `tg://proxy?...` (MTProto), `https://t.me/socks?...`, `tg://socks?...` (SOCKS5), а также `socks5://user:password@server:port` и `http://user:password@server:port` (HTTP CONNECT). Логин и пароль в URL должны быть URL-кодированы. Скопируйте ссылку из настроек прокси официального Telegram; не публикуйте её и не присылайте в чат. Ссылка разбирается локально и не открывается в интернете. Для прокси на самом Windows-компьютере используйте `host.docker.internal` вместо `localhost`/`127.0.0.1`: внутри контейнера loopback указывает на сам контейнер.

Прокси официального Telegram и HTTP/HTTPS-прокси Docker Desktop не становятся настройкой TDLib автоматически. После обновления кода и `docker-compose.yml` выполните `docker compose --profile app build telegram-gateway`, затем `docker compose --profile app up -d --no-build --wait`. При последующих изменениях `.env` достаточно второй команды. Настройка применяется к каждой новой и восстановленной сессии; пустой `TELEGRAM_PROXY_URL` отключает ранее включённый прокси TDLib. При ошибке применения авторизация блокируется, автоматического перехода на прямое соединение нет. Строка журнала `telegram_proxy_configured` подтверждает применение локальной настройки; доступность самого прокси подтверждается состоянием соединения и успешным входом. Адрес, пароль и секрет прокси в диагностику не выводятся. Состояние прокси может сохраняться в зашифрованной базе TDLib; сохраняйте `SESSION_MASTER_KEY` и том `telegramdata` при обновлении.

Нажатие «Отправить» создаёт команду в постоянной очереди. Статус «Отправлено» требует подтверждения TDLib. При неизвестном результате автоматического повтора нет: сначала проверьте официальный Telegram. Ошибочную отправку можно повторить вручную; обычный повтор запроса с тем же ключом не создаёт дубль. ИИ не имеет доступа к методу отправки.

Ключ `SESSION_MASTER_KEY` шифрует сессии и журнал сообщений Gateway. Сохраняйте его вместе с защищённой резервной копией и не меняйте при обычном обновлении. «Отключить» выполняет logout и удаляет локальную сессию и сохранённую переписку этого подключения.

## Настройка AI

В `.env` доступны `AI_PROVIDER=disabled|demo|openai`. Значение `demo` использует явно подписанные синтетические правила без LLM. Для настоящего OpenAI-compatible провайдера:

```dotenv
AI_PROVIDER=openai
AI_API_KEY=your-private-key
AI_BASE_URL=https://api.openai.com/v1
AI_MODEL=gpt-4.1-mini
# При необходимости: тот же рабочий HTTP-прокси, который используется для Telegram.
AI_PROXY_URL='http://USER:PASSWORD@HOST:PORT'
```

Ключ получите на https://platform.openai.com/api-keys и вводите только в локальный `.env`/секреты сервера. Доступ к OpenAI API и его баланс оформляются отдельно от подписки ChatGPT. Провайдер должен поддерживать `/chat/completions` и Structured Outputs (`json_schema`). `AI_PROXY_URL` необязателен: оставьте его пустым для прямого соединения. Для локального прокси Windows используйте `host.docker.internal` вместо `127.0.0.1`, а логин/пароль кодируйте как URL. Значение не выводится в интерфейс или журналы. Прокси применяется только к запросам ИИ. Перенаправления провайдера блокируются, чтобы контекст не отправлялся другому получателю.

После обновления проекта сохраните свой `.env`, `SESSION_MASTER_KEY` и тома. Выполните `docker compose --profile app build api web`, затем `docker compose --profile app up -d --no-build --wait`. Новая миграция добавит разрешения ИИ без удаления существующих данных. При следующих изменениях `.env` достаточно `docker compose --profile app up -d --no-deps --no-build --force-recreate --wait api`.

В «Настройках → ИИ-помощник» видны модель, получатель данных, наличие ключа и прокси. Кнопка «Проверить ИИ» отправляет только короткий служебный запрос, без переписки; провайдер может учитывать его в расходе API. Ошибки ключа, модели, квоты, авторизации прокси и TLS отображаются отдельно. Запрос ограничен 25 секундами, автоматических повторов нет. Совместимость вашего провайдера и ключа проверяется этой кнопкой; автоматические тесты используют локальный HTTP fixture.

Для `source=DEMO`, `mode=CLIENT` дополнительных разрешений не требуется. Для настоящего Telegram:

1. Выберите диалог для CRM, загрузите его сообщения и заполните «Мой бизнес»/продукты/знания.
2. В панели «AI Copilot» нажмите «Оформить разрешение». Владелец или администратор регистрирует проверенную политику источника и её версию, документированное основание прав/согласий, ссылку/номер подтверждающего документа, обоснование проверки и срок действия (до года). Если источник запрещает такую обработку, оформлять разрешение нельзя. Форма сохраняет проверку пользователя и не выдаёт автоматического юридического заключения.
3. Разрешение действует только для конкретного диалога, текущего получателя данных и модели; его оформление не запускает анализ. Нажмите «Анализировать диалог» отдельно. В LLM поступают последние допустимые сообщения и сведения бизнеса; ссылки на документы разрешения в LLM не передаются.
4. При отзыве удаляются рекомендации этого диалога и блокируются новые запросы. Если ответ уже готовился, он не сохраняется после отзыва; уже переданные провайдеру данные отозвать этим действием невозможно. Срок действия, режим CLIENT и актуальные права проверившего администратора проверяются сервером при каждом анализе. Смена модели/получателя требует новой проверки. Исключение диалога очищает его содержимое, разрешения и производные данные.

Универсального переключателя обхода нет. Рекомендации имеют версии контекста, три тона, подтверждённые факты с ID сообщений и пометку устаревания. Вставьте текст в поле ввода, отредактируйте и отправьте вручную. Применение рекомендации и фактическая отправка учитываются отдельно.

Токены сохраняются из ответа провайдера. Стоимость неизвестна, пока не заданы `AI_INPUT_COST_PER_MILLION` и `AI_OUTPUT_COST_PER_MILLION`; отсутствие usage не выдаётся за нулевое потребление.

## Разработка и тесты

Стек: Node.js 24, TypeScript, npm workspaces, Next.js 16/React 19/Tailwind, NestJS 11, Prisma 7 + pg adapter, PostgreSQL, Redis/BullMQ, Socket.IO, TDLib. Общие DTO/Zod-контракты — `packages/shared`, БД — `packages/database`, UI — `packages/ui`, приложения — `apps/web`, `apps/api`, `apps/telegram-gateway`.

```bash
npm ci
npm run env:init
npm run infra:up
npm run db:migrate
npm run dev
```

`predev` генерирует Prisma-клиент и собирает общие пакеты. Web работает на 3000, API на 4000, Gateway на 4101. Для разработки Telegram-ключи необязательны: Gateway загружает TDLib, а UI объясняет недостающую конфигурацию. Если раньше запускали полный Compose, остановите его `web api telegram-gateway` перед host dev, сохранив PostgreSQL/Redis.

```bash
npm run build
npm run typecheck
npm test
npm run test:integration
npm run test:e2e
```

Для e2e нужен `npx playwright install --with-deps chromium` или системный Chromium. Интеграционные тесты и браузерные тесты используют отдельные базы с суффиксом `_test`; тесты не очищают рабочую БД. Локальному пользователю БД нужен CREATEDB либо заранее созданные тестовые базы. Проверяются настоящие PostgreSQL/Redis/BullMQ, изоляция Workspace, политика данных, идемпотентность, Structured Outputs и браузерные действия. TDLib protocol fixtures явно отделены от живой авторизации.

Миграции выполняет `scripts/migrate.mjs` с транзакциями, advisory lock и checksum ledger `_sales_migrations`. Применённые SQL-файлы не меняйте. Prisma Migrate не используется; `prisma migrate deploy` не заменяет этот runner. Обновление MVP добавляет таблицы, сохраняя учётные записи Foundation.

## Production и дальнейшая работа

Для публичного запуска необходимы HTTPS ingress, точный `WEB_ORIGIN`, `COOKIE_SECURE=true`, `API_NODE_ENV=production`, закрытая сеть DB/Redis/Gateway, отдельные migration/runtime DB users, backup/restore и независимый security review. Текущая локальная Compose-конфигурация не является готовым SaaS-развёртыванием. Инструкции по среде — [ENVIRONMENT.md](ENVIRONMENT.md), границы компонентов — [ARCHITECTURE.md](ARCHITECTURE.md), оставшиеся задачи — [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md).
