# Безопасность

## Что реализовано и проверяется

- Пароли: bcrypt cost 12, минимум 12 символов, максимум 72 UTF-8 байта; уникальный нормализованный email. Неизвестный email также выполняет bcrypt comparison, ошибка входа общая.
- Сессии: 256-bit случайные opaque tokens, только хеши в БД, HttpOnly/SameSite=Strict cookies, ротация refresh compare-and-swap, фиксированный абсолютный срок и отзыв при logout/удалении членства.
- В production обязательны HTTPS Origin и Secure cookies; небезопасная конфигурация останавливает API.
- CSRF: точное сравнение Origin на POST/PATCH/DELETE, включая login/logout/refresh. Cookies не используются для разрешения чужого Origin.
- IDOR/tenancy: Workspace извлекается из сессии и живого членства, DTO strict, явные безопасные поля ответа. MEMBER не может менять настройки; OWNER/ADMIN могут.
- Redis rate limits: 600 запросов/IP/минуту по умолчанию (REQUESTS_PER_MINUTE); 5 попыток login/register на комбинацию IP+нормализованный email/минуту. При недоступности Redis изменяемые API не обходят лимит, возвращают 503. За reverse proxy текущий общий IP даёт консервативный общий лимит; не доверяйте произвольному X-Forwarded-For. Production needs separately audited ingress/client-IP configuration.
- Тело JSON ограничено 32 KiB. Malformed JSON/слишком большой запрос возвращают 400/413. Zod не допускает передачу роли/tenant ID через регистрационные или бизнес-поля.
- Helmet на API, заголовки безопасности на web, no-store для API, нет permissive CORS. Ошибки возвращают безопасное сообщение и requestId, без stack traces/SQL.
- Логи ошибок не включают payload, пароль, email, cookies, строку подключения или значения переменных окружения. Аудит содержит actor/workspace/action/time без тел запросов.
- Локальный `.env` игнорируется Git и Docker context, создаётся с правами 0600. Пароли локальной инфраструктуры генерируются случайно. Нет стандартного приложения-администратора.
- Проверка TLS, npm integrity и контрольные суммы миграций сохраняются. Не применяются insecure TLS, игнорирование checksums и пользовательские неподтверждённые зеркала.

## Telegram, содержимое и AI

Privacy Engine проверяет Workspace и режим диалога до чтения, импорта, отправки и анализа. CANDIDATE/EXCLUDED не сохраняют текст в CRM; переход в эти режимы удаляет сохранённое содержимое, анализы, варианты, usage, задачи диалога и связи сделок. Минимальные ID/hash команд остаются для защиты от дублирования; технический аудит не содержит переписки. Retention job очищает старые сообщения и анализы. Backup retention должен управляться отдельно.

TDLib живёт в отдельном Gateway. Каталоги сессий изолированы по Workspace/Connection, native database зашифрована 32-byte HKDF key от SESSION_MASTER_KEY; event outbox — AES-256-GCM. Gateway volume содержит также незашифрованные технические идентификаторы/whitelist/hash команд. Master key хранится отдельно в env и не копируется в образ. Secret chats отключены, self-destruct/protected content исключены, file/message databases TDLib отключены. Вложения MVP не скачивает.

Телефон/коды/email/пароли 2FA передаются текущему шагу TDLib, не сохраняются и не логируются. Управление подключением ограничено OWNER/ADMIN. Auth steps ограничены шестью попытками в минуту на подключение. Gateway закрыт от хоста Compose; внутренние API/события требуют constant-time Bearer token. Требование callback-токена привязано к обработчику, поэтому альтернативный URL с завершающим slash не обходит проверку. Интерфейс передаёт credentials сервера только через env, не браузеру.

Для outgoing command существует постоянный SQLite intent до sendMessage. Неопределённый результат не повторяется автоматически. SENT требует подтверждения источника; известный FAILED разрешает ручную попытку. Это защита от дублей, не гарантия exactly-once для произвольных сетевых отказов или потери volumes.

Внешний AI допускает исключительно синтетический DEMO + CLIENT. Telegram-содержимое запрещено даже для выбранных CRM-клиентов. Контекст ограничен Workspace и объёмом, instructions в бизнес-материалах/сообщениях считаются недоверенными данными. AI не получает tools/send capabilities. JSON output валидируется, CONFIRMED facts требуют ID сообщений из контекста, устаревшие варианты блокируются при применении. Живой Telegram и внешний LLM не проверены с пользовательскими ключами.

Socket.IO проверяет origin/referer, session и живое членство при подключении; tenant rooms изолированы. Refresh/logout отключают socket, expiry timer ограничивает срок. События содержат только ID; чтение данных снова проходит HTTP authorization. Изменение членства после уже установленного socket требует усиления немедленного отзыва до публичного SaaS.

## Границы текущего этапа

Не реализованы email verification, сброс/смена пароля, приглашения, управление активными сессиями и удаление аккаунта из UI, бинарные вложения, квоты и подписки. Это локальный MVP, не законченная публичная SaaS-система. Владелец может удалить контакт с его сделками/переписками, очистить историю, исключить чат и отключить Telegram; полное удаление аккаунта требует административной процедуры.

Срок жизни сессии проверяется при каждом запросе, но уборка истёкших записей пока не автоматизирована. SHA-256 у session tokens безопасен за счёт 256-bit случайности; он не используется как password hash. Ротация одноразовая, но автоматического отзыва всей token family при replay нет. Для одновременного refresh из нескольких вкладок ещё нужен coordination/recovery; внутри одной вкладки есть single-flight.

PostgreSQL RLS пока не включён. Tenant isolation обеспечивают API и составные foreign keys там, где есть связи бизнес-сущностей. Каждый новый endpoint обязан проходить отрицательные cross-workspace тесты. Добавление Prisma-запроса без tenant scope недопустимо.

## До production

1. Threat model и независимая проверка auth/tenant boundaries; email verification, reset, account deletion, ограничения регистрации и очистка истёкших сессий.
2. HTTPS ingress, точный Origin, Secure cookies, отдельно доверенные адреса прокси, rate limits для реальных клиентов, закрытый API. Обработка CSP с nonce для Next.js; мониторинг отказов без персональных payload.
3. Управляемые DB/Redis, проверяемый TLS, отдельный DB user для миграций и ограниченный runtime user, закрытая сеть. Secrets manager, ротация, шифрование дисков/бэкапов, проверка восстановления и RPO/RTO.
4. Механизмы удаления данных и сроков хранения с очисткой производных результатов, технических событий, логов и резервных копий по политике.
5. Для TDLib — изолированные каталоги 0700, шифрование БД/файлов и ключи отдельно; очистка при отключении, отсутствие кодов/2FA-паролей в логах/БД. Не полагаться только на права каталога как на шифрование. Secret chats/защищённые сообщения отключены.
6. AIPolicyGuard до любого вызова LLM. Клиентские инструкции недоверенные; провайдеру недоступны секреты, другие Workspace и отправка сообщений. Источник CLIENT не является согласием на AI.
7. Dependency audit, quotas, fault/restart tests, backup/restore drills, observability и инструкции incident response.
